### 用户操作目标

用户点击“导出诊断”或双击诊断工具，必要时按提示复现一次问题，再回传一个脱敏报告。无需自己找 profile、编辑 YAML、复制控制台日志、输入命令或开启调试端口。

报告必须说明“在哪一步失败、采到了什么证据、错误代码或类别、建议的下一步”，并区分安装检查结果、实际运行结果和未完成检查。采集不到关键错误时明确标记“诊断未完成”和原因，不用“52 文件匹配”替代故障排查通过。

### 后续实现范围

1. **运行时组件诊断**：读取加载状态，以及配置校验、模块解析、依赖服务和存储初始化异常。诊断入口在 OpenBKN 主组件加载失败时仍应可用，不能依赖该失败组件先成功启动。
2. **认证与连接分阶段诊断**：区分 CLI 不可用、未登录/平台不匹配、认证拒绝、网络/TLS/超时、Context Loader MCP 初始化失败及平台目录请求失败。保留服务端错误码与失败阶段；单个 401/403 或通用错误文案不足以判断具体根因。
3. **面板错误与报告对应**：面板优先给出已验证的失败阶段、诊断编号和可执行建议。未知错误不一律指向 Token；报告须保留足够的脱敏技术证据供支持人员判断。
4. **诊断覆盖说明**：每项检查分别记录“通过 / 失败 / 未执行 / 证据不足”。主动连接检查需与被动错误采集明确区分；不执行模型问答或业务写操作。
5. **普通桌面版与 npm 形态**：覆盖 Windows 桌面版和 `dsh web`，并做 macOS 回归；现有 v1 只发现 desktop Host，不能声称已覆盖 npm 形态。

方案选型先核对已有宿主接口与可导出记录，优先复用。若缺少接口，评估独立诊断入口或“诊断启动器”；此处是候选方案，不是已经可用的实现。若需要宿主配合，应列明最低支持版本与未适配环境的降级行为，不能承诺单改外部只读脚本就能取得所有运行时异常。

如采用诊断启动器，必须明确会启动或重启哪些进程、保存哪些状态及如何退出；不得悄悄结束正在运行的 DSH。保持用户操作简单，不以自动重装插件、清除配置或重新登录作为默认排查动作。

### 凭据与状态保护

- 优先采集原操作已有的失败证据；复用既有凭证流程时，仅输出状态或脱敏错误，不导出 Token、认证头、Cookie、密钥或包含秘密的 URL 参数。
- 不复制带 Token 的状态文件，不保存未脱敏错误对象或原始日志；脱敏失败应中止该段导出并标明证据缺失。
- 实机故障场景在独立 profile 中构造。原用户已选状态文件只做哈希比对；如果 DSH 自身正常流程写入状态，单独记录，不把“报告没有 Token”当成“用户状态未改变”的证明。

### 验收条件

| 场景 | 必须取得的结果 |
|---|---|
| Windows 普通桌面版，未开调试端口 | 仍可取得有效故障证据；不得靠要求用户手动开 inspector 才通过验收 |
| 插件未装或发行文件损坏/缺失 | 明确识别安装问题，并与组件初始化失败区分 |
| 缺少/错误 `baseUrl`、模块解析失败、存储初始化失败 | 在真实 Host 中复现并采到对应失败类别；不能只校验文件或地址格式 |
| CLI 不可用、未登录或平台不匹配 | 错误阶段和建议与实际场景一致；不泄漏令牌 |
| 网络/TLS/超时、MCP 或平台认证/权限拒绝 | 记录实际失败阶段和错误码，避免把所有失败归为 Token 错误 |
| 原始错误中混入测试用 Token、认证头及敏感 URL | 导出的报告不含测试秘密，且仍能提供有用的错误类别或明确采集缺失 |
| 正常连接与列出网络 | 正确报告已经实测的步骤；未执行的检查不能显示通过 |
| 诊断接口不可用或收集器失败 | 明确显示“诊断未完成”、原因和可行的支持途径，不生成虚假的健康结论 |

Windows 平台 agent 按固定包、宿主和 CLI 版本回传每项通过/失败/未测、脱敏报告、用户实际操作和状态哈希。macOS 模拟 Host/单元测试只能验证收集与脱敏逻辑，不能替代 Windows 普通桌面版的真实故障验收。
