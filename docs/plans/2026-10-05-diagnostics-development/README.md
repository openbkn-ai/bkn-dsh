# OpenBKN 诊断能力开发交接包

日期：2026-10-05，Asia/Taipei。以下为原始开发计划，不作为当前验收结论。

2026-10-06 更新：被动诊断、独立入口、面板及脱敏导出已实现；主组件失败时的入口隔离有 npm Host 历史运行证据。用户决定统一候选版本为 **-7**，本目录原计划中的 -5 不再是发版安排。主动连接探测、Windows 及合并候选 CI 实机验收仍待完成。当前交接入口为 [统一 -7 范围与验证门槛](../../handoff/2026-10-06-release-7/README.md)。

目标：基于已发布 -4，为普通用户提供「打开 OpenBKN → 导出诊断 → 回传一个 JSON」的排障流程。主组件初始化失败时仍应有可用的诊断入口；报告说明失败阶段、证据和下一步，不能把未知错误都归为 Token 问题。

本包用于安排开发，不是可运行的诊断工具。只包含计划、任务和模板；其中标为待实现的脚本尚不存在。

## 如何分发

1. 把本目录或对应 ZIP 发给主开发 agent，让其从 [主开发任务](AGENT-TASKS.md) 的复制指令开始。
2. 先完成 D0 方案验证，再分配 Host 和 UI 工作；一名 agent 可以顺序完成全部开发。
3. 集成 agent 提供固定候选包、已填写清单和可运行的测试脚本后，再把 [Windows 任务](WINDOWS-VERIFICATION.md) 发给 Windows agent。
4. Windows agent 将结果交回用户，由用户转交主开发核对。计划本身不授权向其他聊天发送消息。

## 排期与依赖

估算为工程人日，包含必要验证，不是 agent 的墙钟时间承诺。不含等待人工浏览器授权、评审、远端构建排队和新增宿主适配。

| 阶段 | 负责人 | 工作量估算 | 依赖 |
|---|---|---:|---|
| D0：独立入口与错误取得方式验证、契约冻结 | 主开发 | 0.5 日 | 固定基线 |
| D1：Host 采集、错误分类、脱敏、连接检查 | Host 开发 | 1–1.5 日 | D0 通过 |
| D2：独立 UI、错误提示、导出 | UI 开发 | 0.5–0.75 日 | D0 契约，可与 D1 并行 |
| D3：集成、包检查、macOS 运行、Windows 场景脚本 | 集成／主开发 | 0.5–1 日 | D1、D2 |
| W：Windows 桌面与 npm 实机验收 | Windows agent | 0.5–1 日 | 固定候选及场景脚本交付 |

合计约 3–5 人日；若 D0 证明必须修改 DSH 宿主，改按 5–8 人日重新估算并列出宿主版本依赖。未通过 D0 时，不能把「只有面板导出」宣布为完整诊断功能。

建议先安排「1 名主开发／集成 agent + 1 名 Windows agent」。需要加速时，再将 D1、D2 分给两名开发 agent。不要让多人同时修改入口、打包清单或协议。

## 交付边界

- 开发新候选版本，暂按 `0.2.0-rc.2-openbkn.0.2.0-5` 规划；实际版本由主开发先检查占用情况，再写入候选清单。-4 已发布，不替换其内容。
- 这次授权是制定计划；本轮没有修改插件或执行发版。执行本计划的 agent 应先核对其收到的执行、推送、CI、PR 和发布授权。
- 主开发交付代码、验证证据和固定包；Windows agent 只验收与清理本轮隔离环境。合并、tag、npm publish、dist-tag 变更留给用户明确放行的发布步骤。
- 不扩大为宿主升级、平台部署、自动修复或此前决定暂缓的浏览器授权等待／取消体验改造。
