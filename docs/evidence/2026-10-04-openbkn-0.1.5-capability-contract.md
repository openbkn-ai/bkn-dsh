## 发现的问题（均非本次修改引入）

第 1 条的文案与归类已在同一分支修复（新增 `result-too-large` 降级原因，实机验证之后改的，只有单元测试覆盖）；响应本身过大的问题未处理。

**更正（2026-10-04 发版后）**：本文初稿和 `-2` 的界面文案把上限写成 `maxResultBytes`（默认 1 MB），是错的。该设置作用在投影之后的结果上，84 条操作投影后只有几十 KB；实际触发的是读取器对原始响应的固定 8 MB 上限，调大 `maxResultBytes` 无效。后续分支把该接口的原始上限放宽到 64 MB、去掉文案里的错误指引，并把 MCP 工具调用超时改为可配置、默认仍是 20 秒：60 秒是平台网关的 504 时限，放宽插件超时只会让失败更慢（对应第 2 条，见下方 `…-3` 验收）。

1. **溯源"平台执行事实"在大 Interaction 上显示"平台不可用"。** BOM 那一轮平台侧有 84 条操作，`/interactions/{id}/operations` 的响应约 31 MB（99% 是各操作的 `output` 原文），超过读取器固定的 8 MB 原始响应上限，被归为 `platform-unavailable`，界面文案是"平台暂时不可达"，与实际原因不符。时间链不受影响。0.1.5 的已发布函数内部会展开大量 `query_object_instance`，这种情况会比 0.1.4 常见。
2. **`execute_tool` / `run_code` 20 秒超时。** "子料分层库存" 在 depth=4/5、以及一次 `run_code` 返回 "Request timed out"（时间链显示 20.0 s）；平台侧对应操作记为 failed。模型改用 depth=3 加指标补齐。
3. **模型仍大量使用 `run_code`**（BOM 那轮 11 次）。脚本内的调用不经过插件守卫，属已记录的限制（方案 B）。
4. 模型尝试了 `run_cypher`（排除工具）一次，被拒后改用受管工具，回答未受影响。

## CLI 0.1.5 补测与登录状态解析缺陷（2026-10-04，`-3` 发布后）

`-2` / `-3` 的验收用的是 CLI `@openbkn/bkn-sdk` 0.1.4，而 README 让 0.1.5 平台的用户装 0.1.5。把 CLI 0.1.5 装到临时目录、通过 `cliPath` 指给插件后补测：

- 三个上游问题（bkn-foundry #2004、#2005、#2006）的复现结果与 0.1.4 完全一致。
- 插件面板首次打开失败：「无法验证 OpenBKN 连接」。

原因是插件对 `openbkn auth status --json` 的解析要求 `baseUrl`、`hasToken`、`expired` 三个字段都在。实际输出（均为真实 CLI 输出，非推断）：

| 情形 | CLI 0.1.4 | CLI 0.1.5 |
|---|---|---|
| 从未登录（空的用户目录） | `{ "hasToken": false }` | `{ "hasToken": false }` |
| 已登录，Token 由 0.1.4 登录存下 | 含 `expired: false` | **不含 `expired`**（源码：算不出过期时间时为 `undefined`） |
| 已登录，执行过一次 `auth token` 之后 | 含 `expired` | 含 `expired` |

对照验证（npm 上的 `-3` 对本地构建的修复包，原版 npm `dsh web`，隔离 `DSH_HOME`）：

| 情形 | 已发布的 `-3` | 修复包 |
|---|---|---|
| `auth status` 不含 `expired`（用包装脚本去掉该字段，其余走真实 CLI 0.1.5） | 「无法验证 OpenBKN 连接」 | 列出 2 个网络 |
| CLI 从未登录（进程 `HOME` 指向空目录，真实 CLI 0.1.5） | 「无法验证 OpenBKN 连接」 | 显示登录入口和平台地址 |

说明：修复包是本地 `pnpm pack` 的，不是 CI 产物，这一轮只用于确认缺陷和修复方向；发版时要按发版闸门在 CI 候选包上重做。「用 CLI 0.1.5 全新登录是否会缺 `expired`」未验证，已写进 Windows 交接文件。「从未登录」这一条在所有已发布版本里都存在，之前没暴露是因为每次测试都先登录了。
