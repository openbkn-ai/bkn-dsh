# 本地 -14：原生 404 与 BOM 分层诊断

日期：2026-10-19，Asia/Taipei。仅使用本机正式 `https://192.168.50.129`；保持社区版、原数据与配置，不部署企业扩展。按用户最新要求，所有新修改留本机，未提交、未推送、没有远端 CI、PR、tag 或发布。

## 结论

原生业务溯源 404 已定位为当前正式社区构建没有挂载该企业扩展路由；标准 Trace、Interaction 和操作记录可读。BOM 至少有四类相互独立的问题：本体与函数/Skill 的业务口径冲突、默认展开深度与全局统计混淆、宿主结果截断后的恢复路径，以及模型的数值转述和文件交付声明。不能统一归因于登录、EE 缺失、上下文容量或插件守卫。

插件仅增加与真实治理边界一致的提示：宿主文件工具仍不可用，使用同一 managed 工具的有界分页，保留原筛选与口径；平台 Sandbox 与本地工作区是不同文件系统。没有新增业务算法、答案仲裁、自动纠错回合、文件搬运或工具放行。**当前本地包及确定性验证通过，真实模型 BOM 仍失败，整体验收未收敛。**

## 原生 404 的证据链

[16 项读取对照](native-route-diagnosis.json)使用原有真实 Interaction `int_7bc9e049376da884ad8af7e06777cc99`，没有新建业务记录或生成解释：

| 读取 | CA 验证的 HTTPS | 直连 agent-observability Service |
|---|---|---|
| 同一标准 Interaction | 200，completed | 200，返回体摘要相同 |
| 同一标准 operations | 200，27 条 | 200，返回体摘要相同 |
| 原生业务 detail / explanations / list | 都是 404，19 字节 `404 page not found` | 完全相同的 404 与摘要 |

这排除了此次 404 由 DSH 渲染、入口转发或过期 CLI 登录造成的解释。标准记录本身存在；不存在记录的标准响应与未挂载路由的响应不同。

运行镜像仍为官方 `agent-observability:0.2.0`，已验证的 ARM64 manifest `sha256:f73b73e6ea2702dde35758333adc4498172477a86865635c6602c9a5c24110dd`，对应正式 Foundry commit `81d5752826f3b3f3f72f3ad4cb1e22d45e99ab4b`。该源码 `src/boot/bootstrap.go` 通过 `enterpriseroute.Mount` 挂载可选扩展；`socket.go` 明确 Community 无注册、无企业路由；`route_boundary_test.go` 的 `TestCommunityDoesNotMountLegacyBusinessProvenanceDataRoutes` 固定该 404 行为。正式 Dockerfile 构建 Core 主程序。有关文件摘要及既有镜像 CI 对应关系在上述 JSON 中；本轮没有重新编译或部署平台。

**只有非空原生业务解释这一项需要具备对应扩展的部署。正式版不等于企业版，也没有因此把整轮开发改为企业版。** 当前继续在正式社区版验证标准记录和诚实降级；企业原生数据条件仍是开放前提，没有自动删除验收门槛。插件对其他部署的 404 继续保留“路由或记录未披露”的中立含义，不从 HTTP 状态猜测许可证或记录删除。

## BOM：业务定义确有冲突，不能替平台裁决

[实际 schema、Skill、函数与 SQL 对照](bom-schema-conflict.json)核对到：

- 本机 `get_object_types` 的 BOM 说明写“BOM 分析默认使用 alt_priority == 0 的主料”；字段注释也写“优先级为 0 的是主料”。替代组内优先级 0 被定义为主料。
- 当前函数实现 `is_main_row` 与 Skill 业务规则同时要求 `alt_priority == 0` **且** `alt_method != "替代"`。本机真实函数响应的 `caliber=main_only` 与这条规则一致。
- [独立只读 SQL](bom-scope-sql-oracle.json)证明两者结果不同，不是插件丢行：

| 口径 | 行数 | 不同物料 |
|---|---:|---:|
| 原始 BOM，含根、含全部替代行 | 507 | 408 |
| 仅优先级 0，去根 | 399 | 333 |
| 当前发布函数 main_only，去根 | 313 | 272 |
| 被额外排除的优先级 0、替代方式为“替代”的子件行 | 86 | 68 |

86 行中部分物料也存在于保留的主料行，所以不同物料数差为 61，不能用 333-68 推导 272。例：`791-000007` 的替代组中存在优先级 0、`alt_part` 为空的成员，以及优先级大于 0、标记为替代件的其他成员。

此前把 399/333 一概称作模型“筛错”不够准确：模型的回退确实改变了函数口径，但与另一份本体说明一致。**SQL 与某条筛选规则一致不代表已确认该业务规则正确。** 已请求用户确认最终口径；确认前不改函数、本体、Skill、样例数据或现有平台配置。`bkn-samples` 中既有的 `tools/preflight.py` 修改未触碰。

库存也须按口径分开：`528-000036` 的全仓可用量为 51（借用仓 16、苏州半成品仓 34、待处理仓 1），生产仓口径为 34。51 本身不是错误；把它声称为生产仓可用量才不一致。不存在库存行也须与测得的零分开。

## BOM：实际读取、截断与文件交付

[-12 原始会话与完整宿主 spill 对照](bom-trace-diagnosis.json)证明两版函数都返回完整的 313 行、272 种、`caliber=main_only`，`next_offset=null`。DSH 向模型展示的文本随后被缩为约 49,933 字符，并附带 30,516 / 30,540 字节省略提示。完整 spill 文件仍存在且与函数字段一致。

宿主提示使用 `read/grep`，而绑定业务会话的既定守卫拒绝宿主文件工具。这是可恢复路径不匹配，不能通过开放任意本地文件访问解决。[-14 旧宿主](bom-pages-0.2.0-rc.2.json)与[新宿主](bom-pages-0.2.1-rc.2.json)均在各自真实 ToolRuntime、McpClient 和宿主 spill policy 中验证：

- 单页 500 的完整响应触发 spill，canonical 值仍保留全部 313 行。
- 同一函数、同样的筛选与 `depth=5`，改为每页 100，返回 100/100/100/13 四页，无 spill；所有行的规范化多重集 SHA-256 与单页原始结果完全一致。
- `read` 与 `present` 都继续被拒绝，工具 execute 未被调用。测试 Interaction 正常 finish；没有模型或文件交付成功的推断。

原 -12 旧模型回合把 CSV 写到了远端 `/workspace/conv-*`，然后调用本地 `present` 被拒；此前实际点击其声称导出的链接，宿主显示文件不存在。新模型回合承认 CSV 仍在平台 Sandbox。两者均不是用户收到完整文件，不能把远端文件存在当成交付成功。

## -14 实际模型复验仍未通过

使用同一本地 tgz、两套原隔离 Mac CLI、原始完整问题、新独立会话、实际响应模型 `deepseek-flash`。两份原生会话均记录到了新增治理指引，排除了只换磁盘文件但宿主未加载的解释。contextWindow=1,000,000、maxTokens=32,768 为此前已记录的隔离测试条件；没有改平台模型配置或修正原回答。

| 宿主 | 实际结束 | 尚未通过的具体证据 |
|---|---|---|
| `0.2.0-rc.2` | completed，22 次工具调用 | 只交付部分层级/物料；把工具中 994-000550 的全仓合计 1,925 写成 94；仍尝试被拒的宿主 read，没有采用较小函数分页 |
| `0.2.1-rc.2` | completed，16 次工具调用 | 函数 depth 未传，返回 depth=1、scoped_line_count=9、next_offset=null；模型却称已取全层第 1 页、尚缺下一页，并询问是否继续，未完成用户原问题要求 |

这里还有一个明确的范围误读：`report_grain=full` 只改变当前 depth 范围内的结果粒度；`line_count` 是全树统计，不等于本次返回行数。旧模型的 depth=2 返回 25 行是 L1+L2 累计，不是 L2 单层 25 行。新模型所称缺下一页，实际首先缺的是请求的展开深度。

数值 94 也不能归咎于宿主省略：旧回合对应 `query_metric` 的 84 行输出未触发 spill，五个仓的 994-000550 数值合计为 1,925；独立 SQL 一致。两次 -14 回合都未再声称已交付远端 CSV，但这不代表全量答案已经正确。[复验概要](real-model-summary.json)、[旧版逐标准评分](BOM-0.2.0-rc.2.md)、[新版评分](BOM-0.2.1-rc.2.md)保留失败；其他问题在此包上记为未执行，没有整轮 G6 通过率。

评分仍以声明的函数快照为参考，不裁决上游业务口径；未满足某项固定参考条件也不意味着另一种清楚说明的仓范围本身错误。模型实际提供的事实分别评分，没有以粗粒度 fail 将所有事实都判错。
